# Run 4 — tvOS hardware: persistence sandboxed, can't save settings or hosts

Logs: [`./2026-05-05-20-37-run4-logs.txt`](./2026-05-05-20-37-run4-logs.txt).
First real-hardware run on Apple TV 4K 3rd gen. Pairing succeeded but
nothing persists across launches; user re-paired twice in this session.

## 1. What is going wrong

Two failure clusters:

**A. Application Support directory writes are denied (BLOCKING).**

- `20:38:25.658305` — `settings.json write failed: NSCocoaErrorDomain
  Code=513 "You don't have permission to save the file 'ChiakiTV' in
  the folder 'Application Support'." NSPOSIXErrorDomain Code=1
  (EPERM, "Operation not permitted")`
- `20:40:02.154411` — same error for `registered_hosts.json` after
  `Regist successfully received response`
- `20:40:42.659789` — same error on the user's second re-pair attempt

Failed path: `/var/mobile/Containers/Data/Application/<UUID>/Library/Application Support/ChiakiTV`.
The `mkdir -p` call inside `JSONFileStore.write(...)` is what's
returning EPERM — `Library/Application Support` itself is not writable
in tvOS sandboxes.

**B. `_UIReplicantView` SwiftUI faults during initial UI layout (cosmetic).**

- 6 occurrences between `20:38:36.032743` and `20:38:41.914400`,
  during the discovery → host-list → pairing-flow navigation:

> "Adding '_UIReplicantView' as a subview of UIHostingController.view
> is not supported and may result in a broken view hierarchy."

UI is functional (pairing completes, host appears, PIN entry works);
this is SwiftUI animation machinery complaining at the runtime-issues
log channel.

## 2. Why it is going wrong

**A.** tvOS sandboxes the `Library/Application Support/` and
`Library/Documents/` subtrees as read-only. The only writable
locations inside the app container are `Library/Caches/` (volatile —
the OS may evict at any time) and `tmp/`. Persistent app state must
live in `NSUserDefaults` or `NSUbiquitousKeyValueStore`. Our store
[`tvos/ChiakiTV/Services/Settings/JSONFileStore.swift:14-19`](../../ChiakiTV/Services/Settings/JSONFileStore.swift)
is unconditionally targeting `applicationSupportDirectory`:

```swift
static let directoryURL: URL = {
    let base = FileManager.default.urls(for: .applicationSupportDirectory,
                                        in: .userDomainMask)[0]
    return base.appendingPathComponent("ChiakiTV", isDirectory: true)
}()
```

The directory creation at line 37–38 then fails with EPERM. This
worked on the simulator because the simulator runs as a Mac process
where `Application Support` is unrestricted; on real tvOS device
sandboxes it does not.

This blocks Phase 1 sign-off because:
- Pairing doesn't persist → user must re-pair every cold launch.
- Settings (PSN account ID, audio volume, etc.) don't persist either.

**B.** `_UIReplicantView` is SwiftUI's transition-animation snapshot
view. The fault fires when SwiftUI inserts it as a subview of the
`UIHostingController.view` during a `.transition(.opacity)`
animation, which is exactly what happens in
[`ContentView.swift:23-26`](../../ChiakiTV/Views/ContentView.swift)
during route changes. tvOS's `UIHostingController` integration
classifies this as a runtime-issues fault because the replicant view
escapes the hosting controller's owned subview list during the
animation. Apple themselves trigger this in many SwiftUI tvOS samples;
it has been a known SwiftUI noise channel since iOS 17 / tvOS 17.

## 3. How chiaki-ng handles it

**A.** Desktop chiaki-ng uses `QSettings` (Qt's plist/registry-backed
KVS) and a JSON file in `QStandardPaths::AppConfigLocation` for
registered hosts ([`gui/src/settings.cpp:57-71`](../../../gui/src/settings.cpp)).
On Mac that resolves to `~/Library/Application Support/Chiaki/`,
which is fully writable on macOS. Not directly comparable — the
constraint is tvOS-specific. Closest reference is the sibling iOS
project, which does write to Application Support successfully because
**iOS allows it**; tvOS does not. So this is a port-only platform
gap that chiaki-ng has not had to handle before.

**B.** Not relevant — chiaki-ng is Qt/QML, not SwiftUI.

## 4. How we differ from chiaki-ng

| | Desktop chiaki-ng | tvOS port |
|---|---|---|
| Settings backend | `QSettings` (plist/registry KVS) | JSON file in Application Support |
| Registered hosts | JSON file under `AppConfigLocation` (writable on macOS) | Same, but path is sandboxed-read-only on tvOS |
| Net result on this platform | n/a | Both stores fail silently; user-facing pairing/settings don't survive cold launches |

The architectural mismatch: we picked file-on-disk JSON for both
stores, which is a reasonable iOS choice but the wrong choice for
tvOS. The correct tvOS-native equivalent is `UserDefaults`, which
also serializes JSON-like state into a sandbox-permitted plist and
provides the same atomicity guarantees we get from
`Data.write(...options:.atomic)`.

---

**Proposed fix (separate step — awaiting approval):**

Replace `JSONFileStore` with `UserDefaultsJSONStore`. Same public
shape (`read<T>`, `write<T>`, `reset`), backed by `UserDefaults`:

```swift
enum UserDefaultsJSONStore {
    static let suite = UserDefaults.standard
    static func read<T: Decodable>(_ type: T.Type, from key: String) throws -> T? {
        guard let data = suite.data(forKey: key) else { return nil }
        return try JSONDecoder().decode(T.self, from: data)
    }
    static func write<T: Encodable>(_ value: T, to key: String) throws {
        let encoder = JSONEncoder()
        encoder.outputFormatting = [.prettyPrinted, .sortedKeys]
        let data = try encoder.encode(value)
        suite.set(data, forKey: key)
    }
    static func reset() {
        suite.removeObject(forKey: "settings.json")
        suite.removeObject(forKey: "registered_hosts.json")
    }
}
```

Both call sites ([`SettingsStore.swift`](../../ChiakiTV/Services/Settings/SettingsStore.swift),
[`RegisteredHostStore.swift`](../../ChiakiTV/Services/Settings/RegisteredHostStore.swift))
keep their existing API; only the backing store changes. Filenames
(`settings.json`, `registered_hosts.json`) become defaults keys.
Sized fine: tvOS UserDefaults supports up to 4 MB per value;
registered-hosts JSON is well under 1 KB per host.

Test changes are minimal — `JSONFileStore.reset()` calls in the
persistence test suite become `UserDefaultsJSONStore.reset()` calls
on a separate test-only `UserDefaults(suiteName:)`.

**Defer to Phase 2:** the `_UIReplicantView` fault. It's noisy in the
log channel but doesn't affect rendering; investigating would mean
restructuring the route-change `.transition(.opacity)` to use a
custom `UIViewControllerRepresentable` host or moving overlays out
of the ZStack — disproportionate effort for a cosmetic warning.

**Recommendation:** apply the persistence fix, retest pairing
persistence on hardware, then proceed with the streaming verification
that this run didn't get to (user only paired, didn't connect).
