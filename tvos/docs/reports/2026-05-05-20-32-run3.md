## 2. Why it is going wrong

**Burst A** — simulator's first-frame UDP delivery on a host-NIC-shared
bridge is jittery. The first 16 video packets of frame 3 arrive split
8/16; chiaki's FEC needs ≥8 source + ≥1 parity to reconstruct, gets
exactly that, but the parity unit is too low to cover the 8 missing
slots (0x7–0xe). The receiver correctly bails, requests IDR, and resumes
once the IDR arrives. No code path under our ownership is involved —
this is `lib/src/streamconnection.c` + `lib/src/fec.c` working as
designed. Nothing to fix on our side.

**Burst B** — first audio render cycle on the simulator races the
hardware-rate negotiation. AudioPlayer creates `AVAudioEngine` at init
([`AudioPlayer.swift:22`](../../ChiakiTV/Services/Audio/AudioPlayer.swift))
*before* the audio session is active, then activates the session inside
`configure()` ([`AudioPlayer.swift:48`](../../ChiakiTV/Services/Audio/AudioPlayer.swift)).
The engine captures hardware params at construction time; one IOWorkLoop
cycle is skipped while the session settles. Sibling project explicitly
calls this out and creates the engine *after* session activation
([`../../../ps-remote-play/PSSwiftPlay/Services/Audio/AudioPlayer.swift:73,186-188`](../../../../ps-remote-play/PSSwiftPlay/Services/Audio/AudioPlayer.swift)):

> "Created in `start()` AFTER audio session activation so it picks up the
> correct hardware sample rate. Creating it at init time captures 0 Hz
> from the unconfigured session, causing NSException on tvOS."

We don't NSException because we override the format on connect, but the
single overload is the same root cause.

## 3. How chiaki-ng handles it

**Burst A** — chiaki-ng has nothing to "handle"; the path is the same
upstream lib code we're using. Desktop sees identical bursts on noisy
LAN connects. Nothing in [`gui/src/streamsession.cpp`](../../../gui/src/streamsession.cpp)
adjusts FEC/IDR behavior per-platform.

**Burst B** — chiaki-ng's desktop audio isn't AVAudioEngine-based, so
not directly comparable. The closest reference is the sibling iOS
project, which creates `AVAudioEngine` after `setActive(true)`
([`PSSwiftPlay/Services/Audio/AudioPlayer.swift:178-188`](../../../../ps-remote-play/PSSwiftPlay/Services/Audio/AudioPlayer.swift)):

```swift
func start() throws {
    if !sessionPrepared {
        try configureAudioSession()      // setActive(true)
        sessionPrepared = true
    }
    let engine = AVAudioEngine()         // engine AFTER session
    self.engine = engine
    …
}
```

## 4. How we differ from chiaki-ng / sibling

**Burst A** — no diff. Same lib, same behavior, expected.

**Burst B** — engine construction order:

| | Sibling (correct) | tvOS port |
|---|---|---|
| `AVAudioEngine()` instantiation | Inside `start()`, after `session.setActive(true)` ([line 187](../../../../ps-remote-play/PSSwiftPlay/Services/Audio/AudioPlayer.swift)) | At init time, before any audio session call ([`AudioPlayer.swift:22`](../../ChiakiTV/Services/Audio/AudioPlayer.swift)) |
| Session activation | First step inside `start()` | Inside `configure()`, *after* engine already exists |

## Verdict

**No fixable bugs that block hardware sign-off.** Both anomaly clusters
are cosmetic on the simulator and likely to be quieter or absent on
real Apple TV hardware (wired or wired-equivalent network, settled
audio route from boot).

**Optional polish (defer to Phase 2 unless it bothers you on hardware):**

1. Reorder `AudioPlayer` to construct `AVAudioEngine` after
   `setActive(true)` — eliminates the single HALC overload warning.
   Mechanical 5-line change. Worth doing during Phase 2 polish, not now.
2. The first-frame packet-loss burst self-resolves via IDR in 110 ms —
   if it persists on real hardware we'd investigate, but on the
   simulator this is expected and matches behavior the desktop sees on
   marginal LANs.

**Recommendation:** proceed to step 2 (real Apple TV 4K 3rd gen hardware
verification). If audio + video + controller all work cleanly there,
Phase 1 is done.
