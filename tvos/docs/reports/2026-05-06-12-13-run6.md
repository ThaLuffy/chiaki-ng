# 2026-05-06 12:13 Run 6 — Post-fix retest, stutter pattern unchanged

Stream: 1920x1080@60 H.265, 15 Mbps target, simulator → 192.168.2.26 PS5.
**Same path / same physical setup as run 5.** What changed: the two `lib/src/takion.c`
patches landed (kernel `SO_RCVBUF` raised from 100 KiB → 4 MiB; takion thread
elevated to `QOS_CLASS_USER_INTERACTIVE` on Apple). See [`../reference/known-issues.md`](../reference/known-issues.md#wi-fi-burst-loss--fec-failure-storm-run5-2026-05-06).

## 1. What is going wrong

The two fixes did **not** move the loss numbers. Stuttering is still continuous.

- Senkusha 10-ping RTT mean **3.769 ms** (run5: 2.944 ms — both fine, both noise-level).
- `Clamping reported packet loss: measured=X% reported_max=5.0%` fires throughout. Window measurements (in observed order): **5.6 / 13.9 / 6.9 / 12.5 / 6.2 / 5.7 / 8.7 / 16.4 / 12.4 / 14.9 / 5.8 / 9.5 / 6.0 / 8.5 / 7.3 / 6.4 / 5.4 / 18.2 / 17.4 / 13.4 / 13.0 / 8.7 / 8.4 / 9.5 / 9.4 / 9.6 / 6.6%**. Median ≈ 8.7%, peaks 18.2% (run 5: median ≈ 6%, peaks 13%).
- FEC failure → `StreamConnection requesting IDR frame` → `Received IDR frame, resuming decode` cycle still recurs roughly every second, the same characteristic ~12-resync-per-stable-window storm.
- `Takion AV reorder timeout: skipping N missing packet(s)` continues to fire constantly with N up to ~25 — packets are missing past the 16 ms reorder window, identical to run 5.

If anything, this run is **slightly worse** than run 5. The fixes are not negative, but they are not the dominant variable here.

## 2. Why it is going wrong

**Two of the run-5 hypotheses are now eliminated:**

- ❌ (b) **UDP receive-buffer overrun** — the kernel buffer is now 4 MiB (~2 s of headroom at 15 Mbps). If the buffer were the dominant cause we would see a marked improvement. We do not.
- ❌ Receive-thread preemption — the takion thread now runs at `QOS_CLASS_USER_INTERACTIVE`. Same null result.

**Remaining hypothesis (a): Wi-Fi burst loss between Mac and PS5.** This now has stronger support: the receive-side pipeline has been fattened end-to-end without affecting outcomes, so the packets are being dropped *before they reach our socket* — i.e. on the air interface itself or the AP. Concretely: airtime contention, retry exhaustion, or interference are wiping packet bursts during sustained 15 Mbps downlink, and Senkusha (single-MTU pings) doesn't surface it because it doesn't stress the link.

## 3. How chiaki-ng handles it

Chiaki-lib still does not "handle" raw airtime loss — it relies on PS5-side FEC parity. Same code paths cited in run 5 (`lib/src/takion.c:45,47,1016`; `frameprocessor.c` parity sweep). With the SO_RCVBUF/QoS patches applied, our receive pipeline now matches or exceeds upstream chiaki-ng's on Apple platforms. There is no protocol-level lever upstream we have not already pulled.

## 4. How we differ from chiaki-ng

After the run-5 patches we are **closer** to upstream chiaki-ng than we were, not further:

- Receive-side capacity (RCVBUF + thread QoS) ≥ desktop chiaki-ng on macOS.
- FEC / reorder semantics are identical (we share `lib/`).

The remaining delta is purely environmental and identical to run 5: simulator-on-Mac-on-Wi-Fi vs. wherever the upstream desktop user runs. The Apple TV 4K target is itself Wi-Fi-only without an Ethernet adapter, so the *production* path will share at least one of the two contended radios with this test.

## Confirmation (post-write addendum, 2026-05-06)

**Ethernet-tethered Mac → 0% packet loss observed in subsequent run.**

This confirms hypothesis (a). The 5–18% per-window loss in run 5 / run 6 is Wi-Fi
airtime burst loss between the Mac and the PS5, *not* anything in our receive
pipeline. The two `lib/src/takion.c` patches remain correct receive-pipeline
upgrades (and worth upstreaming — they help on any Wi-Fi-loaded host), but they
were never going to fix this run's stutter because the packets never reach the
socket.

**Production implication for the Apple TV 4K target:** the success-criterion path
in [`../../CLAUDE.md`](../../CLAUDE.md) (4K60 HDR, sub-16 ms added latency vs.
desktop chiaki-ng) is unreachable over a contended Wi-Fi path. Recommendation
documented in [`../reference/known-issues.md`](../reference/known-issues.md).

The bitrate-drop discriminator (test 2) was not run and is no longer load-bearing
— the Ethernet result settled it.
