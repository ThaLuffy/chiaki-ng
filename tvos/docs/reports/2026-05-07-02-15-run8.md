# 2026-05-07 02:15 — run8: CAMetalDrawable misuse — `presentAtTime` is illegal under `CAMetalDisplayLink`

## 1. What is going wrong

Session bring-up **succeeds completely** this time (the run7 1080p fix held):

- `StreamSession: started against 192.168.2.26 ... 1920x1080 @60fps codec=h265HDR`
- All handshakes pass: ctrl, Senkusha (avg RTT 3.589 ms, MTU 1454 both directions), takion v12, BANG.
- StreamConnection receives streaminfo: video profile 1920x1080, audio 48 kHz / 16 bit / 2 ch / 480-frame.
- `VideoDecoder: rebuilt session (codec=h265HDR vps=24B sps=60B pps=7B)` — VT session built, format description ready, HDR colorimetry attached.
- `AudioPlayer: started` and `StreamSession: connected`.

Then app crashes with `SIGABRT`:

```
*** Terminating app due to uncaught exception 'CAMetalDrawableInvalidOperation',
    reason: '-presentAtTime should not be called when using CAMetalDisplayLink.'
*** First throw call stack:
(
    0   CoreFoundation                      … __exceptionPreprocess
    3   QuartzCore                          … -[CAMetalDrawable presentWithOptions:]
    4   Metal                               … __45-[_MTLCommandBuffer presentDrawable:options:]_block_invoke
    …
)
```

This fires the moment the first decoded `CVPixelBuffer` lands and the renderer attempts to present.

## 2. Why it is going wrong

[`MetalRenderer.swift:155 (post-A.6)`](../../ChiakiTV/Services/Video/MetalRenderer.swift) calls:

```swift
commandBuffer.present(drawable, atTime: targetPresentationTimestamp)
```

That is `MTLCommandBuffer.present(_:atTime:)`. Apple's contract for `CAMetalDisplayLink` is that the drawable handed to the delegate is **already scheduled** for `update.targetPresentationTimestamp`; the app must call the time-less `commandBuffer.present(drawable)` (or equivalently `drawable.present()`). Calling `presentAtTime` on a `CAMetalDisplayLink`-vended drawable is what the runtime exception explicitly rejects (`'-presentAtTime should not be called when using CAMetalDisplayLink.'`).

Phase A.6 added the `CAMetalDisplayLink` migration but kept the `present(_:atTime:)` overload from the prior MTKView path. They're incompatible.

## 3. How chiaki-ng handles it

Not directly comparable — chiaki-ng's desktop renderer uses libplacebo on Vulkan via MoltenVK, not `CAMetalLayer`/`CAMetalDisplayLink`. There is no upstream code path to mirror here.

Apple's own documentation (`CAMetalDisplayLink` — "Working with the display link" section) is the relevant reference: *"After you encode any commands you want, schedule the drawable for display with `MTLCommandBuffer.present(_:)`. Don't call `present(at:)` on a drawable from a CAMetalDisplayLink, because it determines its own presentation time."*

## 4. How we differ from chiaki-ng

This is a **tvOS-port-specific Apple-API misuse**, not a chiaki-protocol divergence. Concrete delta:

- Our [`MetalRenderer.swift:155`](../../ChiakiTV/Services/Video/MetalRenderer.swift) calls `commandBuffer.present(drawable, atTime: targetPresentationTimestamp)`.
- The correct call when sourcing the drawable from `CAMetalDisplayLink.Update.drawable` is `commandBuffer.present(drawable)`.
- `targetPresentationTimestamp` is therefore not for `present(_:atTime:)`; it can still inform decode-pacing telemetry / frame-skip decisions, but it is not the right argument to `MTLCommandBuffer.present`.

---

**Proposed fix:** in [`MetalRenderer.swift:155`](../../ChiakiTV/Services/Video/MetalRenderer.swift), change `commandBuffer.present(drawable, atTime: targetPresentationTimestamp)` to `commandBuffer.present(drawable)`. Drop the unused `targetPresentationTimestamp` parameter from `drawIntoDrawable(_:targetPresentationTimestamp:)` (or keep it for telemetry — caller's choice). One-line change. Phase A.6's vsync-alignment win is unchanged: the drawable is still pre-allocated by the display link for the right vsync — we just stop telling the command buffer to override that.
