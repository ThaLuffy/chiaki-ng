# 2026-05-06 11:05 Run 5 — Stuttering / packet-loss storm

Stream: 1920x1080@60 H.265, 15 Mbps target, simulator → 192.168.2.26 PS5,
Senkusha avg RTT 2.944 ms, session uptime ≈ 25 s, then `Debug session ended`.

## 1. What is going wrong

The session connects cleanly but never reaches steady decode. Concrete numbers from this log:

- Senkusha 10-ping RTT mean **2.944 ms**, max 3.504 ms — round-trip latency is fine.
- `Clamping reported packet loss: measured=X% reported_max=5.0%` fires repeatedly. Window measurements (in order seen): **6.3 / 6.5 / 5.2 / 6.1 / 8.7 / 12.9 / 5.7 / 7.0 / 5.3 / 5.8 / 10.3 / 5.0 / 5.1 / 5.3 / 7.6 / 13.0%**. Median ≈ 6%, peaks 13%.
- Per-frame loss is much worse than per-second loss. FEC inputs like `5+0 / 12+3 units` (= 5 data of 12, 0 parity of 3 — **66% of packets lost** for that frame) recur. FEC successes (`8+3 / 11+4` etc.) are rare.
- Each FEC failure → `StreamConnection requesting IDR frame` → `Received IDR frame, resuming decode` → next FEC failure ≈1 s later. The cycle repeats ~12 times in the captured window.
- `Takion AV reorder timeout: skipping N missing packet(s)` fires constantly with N = 1…25 — packets are missing entirely past the 16 ms reorder window, not just out-of-order.

## 2. Why it is going wrong

**Unknown — root cause investigation required.** Hypotheses, in descending order of fit to the evidence:

(a) **Wi-Fi burst loss between Mac (running the simulator) and the PS5.** The signature — low RTT, sustained high single-digit packet loss with bursty frame-level wipeouts — matches Wi-Fi airtime contention and retry exhaustion, not LAN congestion. Senkusha pings are tiny (single MTU) so they pass; sustained 15 Mbps video stresses the link.

(b) UDP receive-buffer overrun on the simulator's host stack at 15 Mbps. Chiaki sets `SO_RCVBUF` to `0x19000` = 100 KiB (lib/src/takion.c:41,260,348); at 15 Mbps that's ~50 ms of headroom, comfortable in the abstract but *not* if the userspace receiver thread is preempted under simulator scheduling.

(c) Genuine LAN congestion — unlikely on a quiet home LAN, but cannot be ruled out without a wired-Ethernet baseline.

## 3. How chiaki-ng handles it

Chiaki-lib does not "handle" raw loss — it relies on PS5-side FEC parity packets. The reorder + FEC stack:

- `lib/src/takion.c:41` — `#define TAKION_A_RWND 0x19000` (the receive-buffer hint).
- `lib/src/takion.c:45,47` — `TAKION_REORDER_QUEUE_SIZE_EXP 4` (16 entries) and `TAKION_AV_REORDER_TIMEOUT_US 16000` (one 60 fps frame).
- `lib/src/takion.c:1016` — emits the exact "Takion AV reorder timeout: skipping … missing" line we see.
- FEC reconstruction: `frameprocessor.c` (parity sweep before NAL hand-off).

Identical code drives chiaki-ng's desktop builds; the desktop GUI on a wired LAN does not show this pattern.

## 4. How we differ from chiaki-ng

We share `lib/` 1:1 — there is no protocol/FEC delta. The deltas are environmental:

- **Host machine**: simulator runs on macOS userland, scheduled alongside the rest of the dev box. Chiaki-ng desktop runs the same code natively but on whatever machine the user picks; many home setups use Ethernet.
- **Network path**: simulator's UDP exits via the Mac's active interface (Wi-Fi here, almost certainly). On real Apple TV 4K hardware the path is Apple TV → router → PS5; eliminating the Mac removes one hop and one Wi-Fi radio's contention budget.
- **No upstream-side mitigation**: chiaki-ng's GUI does nothing extra here either, so a fix would have to be either (i) eliminate the lossy hop, or (ii) lower bitrate / FEC budget so per-frame loss tolerance grows.
