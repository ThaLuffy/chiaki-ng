# Run 2 — Streaming OK, audio is constant crackling

Logs: not yet captured to file (paste run2 console output to
`./2026-05-05-19-22-run2-logs.txt`). Audio-header parameters are unchanged
from run 1 — see [`./2026-05-05-17-47-run1-logs.txt:121-128`](./2026-05-05-17-47-run1-logs.txt).

## 1. What is going wrong

User-reported, after the VideoDecoder fix landed:

- Pairing PIN flow works (some unrelated UIKit constraint warnings during
  PIN entry — benign tvOS system noise).
- After connect, **video stream works correctly** (no crash, frames render).
- **Audio is constant, non-distinguishable crackling** — sounds like
  uniform white-noise / static, not jittery dropouts of recognisable
  speech or music. Crackling starts as soon as audio output begins and
  persists for the entire session.

Audio header from chiaki-lib (run 1, identical here):

```
channels = 2
bits = 16
rate = 48000
frame size = 480
```

Per audio frame on the wire: variable-length **Opus packet** (compressed,
typically 100–400 bytes). Per decoded frame: 480 samples × 2 channels ×
2 bytes = **1920 bytes of int16 PCM**. The two are not the same byte
stream — that distinction is the bug.

## 2. Why it is going wrong

Bridge wires the session's audio sink **directly** to our trampolines —
which means our trampolines receive **raw Opus packets**, not decoded PCM.
[`tvos/ChiakiBridgeC/src/chiaki_bridge_session.c:122-128`](../../ChiakiBridgeC/src/chiaki_bridge_session.c):

```c
static void chiaki_tv_audio_frame_trampoline(uint8_t *buf, size_t buf_size, void *user)
{
    struct chiaki_tv_session *self = user;
    if(!self || !self->audio_frame_cb) return;
    self->audio_frame_cb((const int16_t *)buf, buf_size, self->audio_user);
}
```

…and [`chiaki_bridge_session.c:187-192`](../../ChiakiBridgeC/src/chiaki_bridge_session.c):

```c
ChiakiAudioSink audio_sink = {
    .user = self,
    .header_cb = chiaki_tv_audio_header_trampoline,
    .frame_cb  = chiaki_tv_audio_frame_trampoline,
};
chiaki_session_set_audio_sink(&self->session, &audio_sink);
```

The session's audio sink (per [`lib/src/audioreceiver.c:206-262`](../../../lib/src/audioreceiver.c))
fires `frame_cb` with **the raw payload pulled from the Opus jitter buffer**
— still encoded. The cast `(const int16_t *)buf` reinterprets compressed
Opus bytes as int16 PCM samples. We then memcpy those bytes straight into
an `AVAudioPCMBuffer` ([`AudioPlayer.swift:90-93`](../../ChiakiTV/Services/Audio/AudioPlayer.swift))
and schedule them. AVAudioEngine plays the compressed bytes as if they
were PCM → uniform broad-spectrum noise → crackling.

## 3. How chiaki-ng handles it

Desktop chiaki-ng inserts a `ChiakiOpusDecoder` between the session and
the application. [`gui/src/streamsession.cpp:372-375`](../../../gui/src/streamsession.cpp):

```cpp
chiaki_opus_decoder_set_cb(&opus_decoder, AudioSettingsCb, AudioFrameCb, this);
ChiakiAudioSink audio_sink;
chiaki_opus_decoder_get_sink(&opus_decoder, &audio_sink);
chiaki_session_set_audio_sink(&session, &audio_sink);
```

The opus decoder owns the session sink. Its frame_cb decodes via
`opus_decode` and only THEN forwards int16 PCM to the application
([`lib/src/opusdecoder.c:85-99`](../../../lib/src/opusdecoder.c)):

```c
int r = opus_decode(decoder->opus_decoder, opus_buf, (opus_int32)buf_size,
                    decoder->pcm_buf, decoder->audio_header.frame_size, 0);
…
decoder->frame_cb(decoder->pcm_buf, (size_t)r, decoder->cb_user);
```

`r` is per-channel sample count returned by libopus. The application
receives `int16_t *` buffer + samples_count, not raw bytes.

## 4. How we differ from chiaki-ng

| | chiaki-ng (correct) | tvOS port (buggy) |
|---|---|---|
| Session sink owner | `ChiakiOpusDecoder` (gets sink via `chiaki_opus_decoder_get_sink`) | Our trampolines, registered directly |
| What `frame_cb` receives | Decoded `int16_t *pcm`, `samples_count` | Raw Opus payload, `byte_count` |
| Decoder lifecycle | `chiaki_opus_decoder_init` / `_fini` in session create/destroy | Not present |

We never instantiate a `ChiakiOpusDecoder`, never call
`chiaki_opus_decoder_set_cb`, never call `chiaki_opus_decoder_get_sink`.
The cast in `chiaki_tv_audio_frame_trampoline` is the load-bearing
mistake — the compiler accepts it, the runtime doesn't crash, and the
sample-count math (`byteCount / 4` in [`AudioPlayer.swift:83`](../../ChiakiTV/Services/Audio/AudioPlayer.swift))
even produces a plausible non-zero frame count for a 200-byte Opus
packet, so nothing logs an error — it just renders garbage as audio.

The header trampoline is fine in itself but currently fires before the
PCM path it controls is wired through a real decoder; reusing it after
the fix is straightforward.

---

**Proposed fix (separate step — awaiting approval):**

1. Add `ChiakiOpusDecoder opus_decoder` to `struct chiaki_tv_session`
   ([`chiaki_bridge_session.c:27-40`](../../ChiakiBridgeC/src/chiaki_bridge_session.c)).
2. After `chiaki_session_init` succeeds, call `chiaki_opus_decoder_init`.
3. Replace the `chiaki_tv_audio_frame_trampoline` registration: instead
   of using it as the session sink, register it as the **opus decoder's**
   frame callback (signature is already compatible with what we want —
   `int16_t *buf, size_t samples_count, void *user`). Update the trampoline
   to forward `samples_count * channels * 2` bytes to the Swift callback,
   keeping the existing `(const int16_t *pcm, size_t pcm_byte_count)`
   contract on the Swift side so `AudioPlayer.swift` is unchanged.
4. Get the opus decoder's sink via `chiaki_opus_decoder_get_sink` and
   register THAT with `chiaki_session_set_audio_sink`. Keep our header
   trampoline; it can stay on the session sink path indirectly via the
   opus decoder's settings_cb, OR we hand it directly to the opus
   decoder and stop registering it at the session level. Picking the
   second keeps the contract simple.
5. In `chiaki_tv_session_destroy`, call `chiaki_opus_decoder_fini` before
   `chiaki_session_fini`.
6. Add `#include <chiaki/opusdecoder.h>`.

No Swift changes required. The Swift `AudioPlayer.configure(...)` and
`enqueue(...)` already correctly handle int16 interleaved PCM — they were
never the problem; they were just being fed compressed bytes.
